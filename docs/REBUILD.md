# 既存機能の見直し — v1.18.0

比較基準は v1.17.0（`44067eca19fa364cd4fc88dd37292c59251fa47b`）。既存の期間条件、保存設定、Chrome向け配布とGPLの帰属を維持し、一覧更新・設定保存・クライアント連携の失敗経路を見直す。

## 完成条件

- 一覧の最初の更新、行・tbodyの差し替え、ツールバーのオン・オフ後も、選択・フィルターが動作する。
- 個別機能の失敗によって後続機能の初期化や設定反映が中断しない。
- 保存失敗を成功表示にせず、移行を再試行しても新しいローカル設定を旧同期データで上書きしない。
- サイトを開いていない状態からも実在する設定画面を開ける。サイト上の設定変更にcontent scriptで使えないtabs APIを要求しない。
- クライアント追加APIの失敗を成功とせず、同じ項目の並行送信を重複排除する。外部応答の待ち時間を制限する。

## 選んだ変更範囲

| 選択肢 | 評価 |
| --- | --- |
| 不具合箇所だけに条件分岐を追加 | observerとShow more、設定画面とpopupの異なる経路が残り、状態不整合を再発させやすい |
| 更新・保存・通信の共通部分を整理 | 既存の機能とデータを維持し、問題が起きる境界を直接検証できるため採用 |
| 全UI・全機能の全面置換 | 元の外部連携・作品情報・設定の移行負担に見合う根拠がないため今回は採用しない |

## 再現で分かったこと

- 設定移行と保存の4ケースは、v1.17.0の実装ですべて失敗した。新しいローカル値の上書き、移行失敗中の既存値の見失い、コピー後の移行再試行による上書き、保存失敗時の成功コールバックを確認した。
- 一覧observerは最初の変更を捨て、最初のtbodyだけを監視していた。Show more以外から追加された行には選択欄を追加する経路がなかった。
- `pages/settings/index.html` を参照するナビゲーションがある一方、配布物にはそのページが存在しなかった。
- クライアント応答の形式は各APIの契約に合わせる。HTTP 2xxだけで追加成功と判断しない。

最終テスト結果と制限は [QA記録](QA.md) に記載する。テストはローカルの架空データと制御したAPI応答を使用し、実サイトの利用や実クライアントへの追加と同一視しない。
